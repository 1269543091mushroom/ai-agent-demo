# 半导体行业求职小助手 ·  AI Agent（工具调用 + 评估报告）

一个用 **Python 标准库手写** 的最小 AI Agent，配套一套 20 条样本的评估数据集与评估报告。

核心设计：**模型不执行任何实际操作**，它只输出「要调用哪个工具、传什么参数」；真正的数据查询和计算由本地代码完成，
结果再回传给模型组织成回答。整个过程在终端里逐步可见，方便逐行解释和调试。

## 项目速览

| 项目 | 说明 |
| --- | --- |
| 做什么 | 半导体/存储行业岗位问答助手：查岗位明细、统计数量与薪资、做数字计算，回答里的每个数字都能追溯到工具返回值 |
| 技术要点 | 手写 Agent 循环、OpenAI 兼容接口的 function calling、工具参数清洗与校验、用评估指标驱动提示词迭代 |
| 代码规模 | `agent.py` 534 行 + `run_eval.py` 160 行（含注释），**无第三方依赖**，只用标准库 |
| 模型接入 | 任何 OpenAI 兼容接口均可：DeepSeek / 通义千问 / 智谱，改 `config.txt` 两行即可切换 |
| 实测结果 | 20 条评估样本：工具选择正确率 **100%**、关键点命中率 **100%**、平均 2.38 秒/条、平均 2.15 步、0 条出错（deepseek-chat，2026-10-12） |
| 数据来源 | `data/jobs.csv` 是**作者构造的 20 条演示数据**，用于演示机制，不代表真实招聘信息 |

## 一、快速开始（三条命令）

需要 Python 3.8+（开发环境为 3.15）。无需安装任何依赖。

```bash
# 1. 配置模型密钥：把 config.example.txt 复制成 config.txt，在 api_key= 后面填上密钥
#    （也可以改用环境变量 LLM_API_KEY / LLM_BASE_URL / LLM_MODEL，优先级更高）

# 2. 问一句，观察工具调用过程
python agent.py "合肥和上海的岗位数量差多少？"

# 3. 跑评估，生成 eval_report.md
python run_eval.py
```

其它用法：

```bash
python agent.py                     # 交互模式，可以连续提问
python agent.py --mock "合肥有哪些岗位？"   # 离线模式：不联网、不调用模型，仅验证流程
python run_eval.py --mock           # 离线跑一遍评估流程
```

## 二、它解决什么问题

大语言模型有一个典型问题：你问它「合肥有多少个岗位在招」，它会理直气壮地给出一个数字，而这个数字是"续写"出来的，
无法追溯。工程上的解法不是让它"更诚实"，而是**把事实性数据从模型里拿出来，交给工具**：

| 问题 | 处理方式 |
| --- | --- |
| 岗位、薪资、数量从哪来 | 只能来自工具（本地数据/未来接数据库、API），模型不得凭印象回答 |
| 算术运算 | 交给 `calculate` 工具，且用白名单正则限制成纯算术表达式 |
| 闲聊、能力询问 | 系统提示词明确规定：不调用任何工具 |

## 三、架构：五层分离

每层职责单一，代码里按相同顺序分节（括号内为 `agent.py` 中的行区间）：

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 配置层 | `agent.py` 46–67 | 读取密钥与模型设置，环境变量优先于 `config.txt` |
| 数据层 | `agent.py` 68–103 | 读 `data/jobs.csv`，返回结构化岗位记录 |
| 工具层 | `agent.py` 104–267 | 三个工具 + 工具说明书（JSON Schema）：`search_jobs` / `salary_stats` / `calculate` |
| 模型层 | `agent.py` 285–319 | 调 OpenAI 兼容接口，`temperature=0`，把工具说明书一并下发 |
| 编排层 | `agent.py` 408–473 | Agent 循环：模型决策 → 执行工具 → 结果回传 → 再决策，直到给出最终回答 |

角色设定（system prompt）单独放在 `agent.py` 268–284，明确写了"工具结果是唯一事实来源""工具没查到就如实说明，不许编造岗位"
——这部分对应 JD 里的「角色设定 / 提示词工程」。

## 四、Agent 循环

核心逻辑不到 30 行，循环体做四件事：

```
for step in 1..MAX_STEPS(6):
    把 messages 发给模型
    如果模型要调工具：
        本地执行工具 → 把结果作为 role=tool 的消息追加进 messages → 继续循环
    否则：
        返回模型的最终回答，结束
```

一次真实运行的终端输出（问题：合肥和上海的岗位数量差多少）：

```
用户提问：合肥和上海的岗位数量差多少？
  [第1步] 调用工具 salary_stats({"city": "合肥"})
           返回：{"范围": "合肥", "岗位数": 14, "平均月薪": 11804, ...}
  [第2步] 调用工具 salary_stats({"city": "上海"})
           返回：{"范围": "上海", "岗位数": 6, "平均月薪": 19750, ...}
  [第3步] 调用工具 calculate({"expression": "14-6"})
           返回：{"表达式": "14-6", "结果": 8}

[最终回答] 合肥比上海多 8 个岗位：合肥 14 个，上海 6 个。（数据来自本地岗位库）
```

这条链路同时体现了**多步编排**（连续三次工具调用）和**数字可追溯**（8 = 14 − 6，两个 14/6 都来自工具）。

## 五、工程细节（为什么这么写）

- **`temperature=0`**：同样的输入尽量得到同样的输出，评估结果才有可比性。
- **最大步数 `MAX_STEPS = 6`**：防止模型反复调工具停不下来，超限时返回明确的错误标记，而不是卡死。
- **计算器白名单**：`calculate` 只接受匹配 `^[0-9+\-*/(). ]+$` 的表达式，避免把模型输出当代码执行。
- **参数清洗 + 校验**：模型给的参数先清洗（丢多余字段、统一成字符串、数值转换），若环境里装了 `jsonschema`
  还会按工具定义做严格校验；**校验失败不抛异常，而是把失败原因作为工具结果回传给模型，让它自己改**。
- **工具失败可解释**：工具内部报错会变成一条结构化结果回传，模型可以据此调整或如实说明，而不是整个程序崩掉。
- **密钥不写死在代码里**：优先读环境变量，其次读本地 `config.txt`；仓库里只有 `config.example.txt` 模板，不含任何密钥。

## 六、评估：数据集、指标与结果

这是本项目区别于"演示 Demo"的部分 —— **有数据集、有指标、可复现、可用于比较改动前后**。

**数据集** `eval_dataset.json`：20 条样本，每条标注期望调用的工具（`expected_tool`）、回答中必须出现的关键信息
（`expected_keywords`）和考点（`point`）。覆盖范围：

| 类型 | 条数 | 例子 |
| --- | --- | --- |
| 岗位检索（单条件 / 多条件 / 口语化） | 10 | 「上海的数字IC验证工程师要求什么学历？」 |
| 统计（数量、均值、比较、排名） | 5 | 「哪个城市岗位更多？」（口语句式，未出现"统计"二字） |
| 计算 | 2 | 「帮我算一下 15万除以12是多少」（需先把 15万 换算成数字） |
| 多步编排 | 2 | 「合肥的工艺工程师和上海的工艺工程师薪资差多少？」 |
| 不该调工具的闲聊 | 1 | 「你好，你能帮我做什么？」——考验工具调用边界 |

**指标定义**：

- **工具选择正确率** = 该调工具时调了预期工具、且不该调时一次都没调的比例（"不该调"单独作为一类样本考核）
- **关键点命中率** = 最终回答里包含预期关键信息的比例（一条样本列多个关键词时命中任意一个即通过，对措辞差异更宽容）
- **平均耗时 / 平均工具调用步数** = 反映响应速度、任务复杂度与调用成本

**实测结果**（deepseek-chat，2026-10-12，20 条样本全部调用真实模型）：

| 指标 | 结果 |
| --- | --- |
| 工具选择正确率 | 20/20 = 100% |
| 关键点命中率 | 20/20 = 100% |
| 平均耗时 | 2.38 秒/条 |
| 平均工具调用步数 | 2.15 步 |
| 出错条数 | 0 |

`python run_eval.py` 会重新跑一遍并生成 `eval_report.md`（含总体指标、逐条明细、失败样本与改进方向）。

**这套评估的用途**：改提示词或工具描述之后重跑，用指标判断改动是变好还是变坏，而不是凭感觉。评估脚本会在
失败样本里标出"工具选错"还是"关键点没命中"，对应两类不同的修法：前者多半是工具 `description` 写得不够具体，
后者多半需要在 system prompt 里补约束。

## 七、可以怎么验证（建议面试官现场做的三个动作）

1. `python agent.py "合肥和上海的岗位数量差多少？"` —— 应看到连续三次工具调用（统计 → 统计 → 计算），验证多步编排。
2. `python agent.py "你好，你能帮我做什么？"` —— 应看到**零次**工具调用，验证工具调用边界。
3. `python run_eval.py` —— 20 条样本逐条打印通过情况，并生成评估报告；可以改一条 system prompt 规则后重跑，
   对比两次数值。

没有密钥也可以先跑 `python agent.py --mock "合肥有哪些岗位？"` 验证流程（离线规则模拟，不代表模型效果）。

## 八、已知不足与下一步

1. **数据与检索**：`data/jobs.csv` 是构造的演示数据，检索用的是关键字段匹配，不是语义检索。下一步：接入数据库或
   内部 API，把关键词匹配换成 embedding 检索（即 RAG 的常规做法），并在工具层做分页与权限控制。
2. **评估样本量偏小**：20 条只能发现明显问题，指标对单条样本敏感。下一步：扩到百条量级，按题型分层统计，
   并引入人工/模型打分处理主观质量。
3. **上下文管理**：目前没有多轮历史的裁剪或摘要，对话变长后会超出上下文窗口。
4. **成本与路由**：单 Agent 单线程，简单问题也走同一个模型。下一步：按问题复杂度路由到不同模型。
5. **服务质量**：没有鉴权、限流、超时重试与缓存，做成对外服务前必须补齐。
6. **失败归因较粗**：现在只统计"工具/关键点"是否通过，尚未对失败原因做分类统计。
